# Blueprint Agent Instructions

This folder is an app-owned Blueprint sidecar. Work sidecar-first and preserve the authority of each layer:

- Start with the Blueprint MCP `validate` tool using `{ "project": "<this-folder>" }`, then use `index` to discover stable boundary IDs. Use focused `query` calls and deep `extract` packets before reading the canvas DOM. Every validation error names the field and ends with `Fix:` and the exact change to make. Apply each fix as written.
- Every structured file carries `"schemaVersion": "3.0.0"`. When a tool reports a file on an older schema, run the `migrate` tool, with `dryRun: true` first to see what it changes. `validate` reports each file on an older schema and `serve` shows a notice. `serve` with `focus` or `explorationId`, and every other tool that reads the folder, refuse it until then. Migrate applies every mechanical change itself and returns the validation of the result. Each remaining error is a decision for you, such as a component's platforms or a page's description. Fix them all before other work.
- A running MCP server keeps its tool code, tool text, and canvas page from the build that started it. Its validation workers and the starter come from the build on disk. After a new Blueprint build, the canvas page of a running server cannot load its script, and a second `serve` call does not fix the page. Ask the person to restart the MCP server of each session on this folder, because the sessions share one runtime. Then run `migrate`.
- Structured JSON owns stable IDs, declarations, named states, dependency relationships, production relationships, targets, review conditions, and saved exploration/history metadata. Keep `manifest.json`, `brand.json`, `tokens.json`, `primitives.json`, `components.json`, and `screens.json` internally consistent; keep each saved comparison in `explorations/<id>.json` and each prior canonical version in `history/<screen>-v<n>.json`.
- Every primitive, component, and screen declares governed HTML/CSS; there is no source-less format. Governed primitive HTML/CSS is the canonical reusable implementation. Primitive pages, components, and screens must instantiate that same source. Governed component HTML/CSS owns reusable assemblies. Screen HTML/CSS owns unique semantic hierarchy, responsive layout, media, effects, and art direction.
- Compose reusable boundaries with `<blueprint-use kind="primitive|component" ref="<stable-id>" variant="<variant>" size="<size>" state="<state>">`; an omitted attribute takes that axis's default. Declare every rendered reusable dependency in JSON; do not duplicate a recurring control in screen-local markup or add an app-specific Blueprint runtime branch. Blueprint replaces the authoring element with the referenced app root and annotates that root directly, so write layout selectors against semantic component/primitive roots rather than `<blueprint-use>`.
- Slot content belongs to the source that wrote it. A reusable placed inside another reusable's slot (a `text` label in a dialog, an `icon-tile` in a row's leading slot, a `status` in a table cell) is declared on the screen section or component whose HTML contains it, not on the container. Only declare it on the container when every instance of that container renders it; the container then keeps the credit. Slot elements match by balanced tags, so slot content may nest the same tag.
- Use token CSS custom properties for reusable colors, type, spacing, sizing, shape, shadow, and motion. Theme the app by changing the values of the existing roles in `tokens.json`; add a role only for a genuinely new meaning, never a parallel palette that restates existing roles. Record deliberate screen-local literals in `prototype.localValueExceptions` with the exact CSS property and the whole declaration value. Validation in each mode rejects undeclared color literals, named colors, and lengths that restate a same-role token. A unique composition length stays legal. Instantiate control primitives with `<blueprint-use>` rather than hand-building native buttons, inputs, or selects; mark a deliberate native control with `data-blueprint-native="<reason>"`.
- Validation in each mode rejects these items in a source or a stylesheet, and each error names the fix:
  1. A `style` attribute, a `<style>` element, and `!important`. Put each declaration in a stylesheet of the boundary.
  2. A raw `font-family` or `font-size`, also inside a `font` shorthand. Use `var()` of a typography token, or `inherit`. An entry in `prototype.localValueExceptions` does not excuse it.
  3. A custom property that a stylesheet declares, and `var()` of a name that no token declares. Add the value to `tokens.json`, or write the value in the rule. The compiler sets `--blueprint-safe-area-*` and `--brand-accent`.
  4. A selector that does not start at the root of its boundary. Start it with `[data-blueprint-<kind>="<id>"]`, with a class in the namespace of the boundary such as `.button__label`, or with `:where()` of that root.
  5. A rule on the root of another reusable that sets a property other than margin, size, flex and grid placement, order, self alignment, or `display: none`. A class on `<blueprint-use class="x">` lands on that root, so a rule on `.x` follows this limit too. Add a variant to that reusable for each other property.
  6. A selector whose subject is a class in the namespace of another boundary, such as `.button__label` in a screen. This applies to each property. Add a variant to that reusable, and put the rule in its stylesheet.
  7. A selector that goes through the root of another reusable, or through a forwarded class, to an element without a class in the namespace of this boundary. Add a variant to that reusable, or give the element a class of this boundary.
  8. A selector whose subject is only a type or `*`, in a boundary that places a reusable, when a descendant combinator can cross into that reusable. Give the element a class of this boundary, or use a child combinator from an element that this boundary owns. A class on an element that holds no `<blueprint-use>` stays legal as the anchor. A universal rule that sets only `box-sizing` stays legal.
  9. An inline `<svg>` in a screen or a component, outside a `<blueprint-use>` and outside a slot. Put it in `<blueprint-use kind="primitive" ref="icon">`, or use a brand mark when it is a logo.
  10. A literal color in `fill`, `stroke`, `stop-color`, `flood-color`, `lighting-color`, or `color` on an element of an `<svg>` in a prototype source. Use `none`, `currentColor`, or `var()` of a token. Brand mark files stay under the brand rules.
  11. `srcset`, and an `href` to a file on `<image>`, `<feImage>`, or `<use>`. Load each file through `src` with the file in `prototype.assetRefs`.
  12. Placeholder text in a prose field or a ref, such as `TODO`, `TBD`, lorem ipsum, or a value in angle brackets.
- Validation also runs these rules on each candidate of an active exploration, and each error names the candidate file. Validation does not run them on a frozen baseline or on a history record. `restore` refuses a history record that fails a rule, and its error names the history file.
- `serve` and `inspo` stop only on a contract error. The canvas opens with style errors, so that a person can review the finding marks. `serve` returns `styleErrorCount` and the first `styleErrors`, and `validate` lists each one. `explore` create, `promote`, and `restore` stop on each error. An `explore` archive stops only on an error that it adds.
- Each token value must parse as its type. A `color` is a CSS color or a gradient. A `space` or `radius` is a length, a percentage, `0`, or a math function. A `size` is one of these, a plain number, or a grid track list. A `typography` value is a `font` shorthand, a family list, or a length. A `shadow` is a CSS shadow. A `motion` value is a duration, an easing, or both. Each `styleRef` starts with `--app-`, and a color token id appears in one group only.
- Surfaces nest sequentially. Roots marked `data-blueprint-surface` (surface, card, grouped list, pressable row) take the next level of the `color.surface` to `color.surface-6` ladder after their nearest marked ancestor, so a card inside surface 3 renders at level 4. Mark app-added container primitives the same way instead of assigning them a fixed fill.
- Phone frames render the screen full-bleed at the preset size with the iOS status bar and home indicator drawn over it, as on device. Keep content clear of them with `var(--blueprint-safe-area-top)`, `-right`, `-bottom`, and `-left`, which every compiled screen receives from its frame preset; do not hard-code insets or draw status bars in screen source. Browser frames keep their toolbar outside the preset viewport.
- Keep fonts, images, and media inside `manifest.prototypeHost.assetRoots`, list screen assets in `prototype.assetRefs`, and keep sources self-contained. Do not add remote assets, undeclared filesystem refs, arbitrary JavaScript, or nondeterministic runtime state. Review links must remain safe local destinations and compile to inert metadata; forms must not declare actions or submitting controls in the static no-network slice.
- A new sidecar starts with exactly two empty base frames: `screen:home` on `phone` and `screen:web-home` on `desktop-web`, each backed by an empty screen source. Map real app tokens and recurring controls, then fill those sources before adding more routes or states. Do not invent product copy to fill an empty canvas.
- Keep frame naming structured: `productionRelationship.routePath` owns the route and `name` owns the short plain-language frame name. Blueprint derives the visible `Route · Frame name` label. If multiple screen records intentionally share both values, give every one a unique consecutive positive integer `version` starting at `1`; Blueprint then appends `· Vn`. Omit `version` for a single frame, and do not put routes, machine IDs, states, viewports, or version markers inside `name`.
- Use the MCP `explore` tool for two to five alternatives to one exact screen state and viewport. Edit only the returned candidate HTML/CSS sources, use exploration queries and `serve` with `explorationId` for review, and do not add candidates to `screens.json`. Leave unresolved explorations active or archive them; never delete their saved baseline or candidate sources. Call `promote` only after the person explicitly chooses a candidate and supply all current digests returned by inspection so stale work cannot overwrite a newer canonical screen silently. Use history queries plus `restore` when the person chooses a prior version; restoration must preserve the outgoing current screen as the next immutable history entry.
- `primitives.json` carries the closed Blueprint primitive set: the 33 building blocks every app shares, from button and input to table row. Keep exactly this set and never add or delete a primitive. Blueprint owns each primitive's id, name, group, platforms, defaults, its floor of variants, sizes, states, and slots, and the text that describes them. Primitives take on this app's design through token values. Restyle their sources and add variants, sizes, states, and slots above the floor as the app needs. An app-specific piece, such as a bento grid, a stat chip, or a rank emblem, is a component in `components.json` built from primitives. Validation in each mode rejects primitives outside the set and values below the floor. Strict validation rejects each deleted primitive, and baseline validation rejects most of them.
- Primitives and components are reusables: presentational pieces that receive data and present it by the rules of the foundations, with no business logic. Both are written in one shape, and every field is required: `id`, `name`, `description`, `group`, `platforms`, `uses`, `variants`, `sizes`, `states`, `unsupported`, `slots`, `prototype` (`source`, `styles`, `localValueExceptions`), `tokenGroupIds`, `tokenRoles`, `accessibility`, `notes`, `implementationHints`, `implementationTargets`, `styleRefs`, `styleEvidence`, and `prototypeOnly`. Validation rejects any other field, so put nothing else on a reusable.
- Ids are kebab-case. Names are sentence case and at most 32 characters, such as "Empty state", not "Empty State"; descriptions say what it is and when to use it in at most 200 characters.
- Validation applies these rules to names and ids, and each error names the fix:
  1. An id has at most 36 characters.
  2. The id of a primitive, a component, a screen, a page, a section, an active exploration, or its candidate says what it holds. It holds no placeholder word such as `new`, `temp`, `test`, `thing`, `misc`, or `copy`, no version word such as `v2`, `final`, `old`, or `alt`, and it does not end in a number. The id of a primitive or a component holds no generated part, such as a hash.
  3. A screen id can end in `-v<version>` when `version` of that screen holds the same number, 2 or greater.
  4. A screen id is unique in the project. Each pair of screen name and version is unique in the project, so two routes cannot share a name. Numbered versions of one route keep a shared name.
  5. A name is unique among primitives, among components, and among pages. A component id does not equal a primitive id.
  6. The source of a reusable is `prototype/<kind>s/<id>.html`, and its root element sets `data-blueprint-<kind>="<id>"`.
  7. A screen state id, a review condition id, a frame preset id, and a brand mark id are kebab-case.
  8. An axis with one value uses the id `default`. The `migrate` tool renames the value when it can do so safely.
- Blueprint does not make a numbered id. The `explore` tool makes each id from the title and the labels that you pass, and it refuses a name that is already in use. Pass another descriptive name.
- `variants`, `sizes`, and `states` are each `{ "default": "<id>", "values": [{ "id", "name", "description" }] }` with at least one value. A variant is a design choice the placement keeps, such as primary or ghost, a tone, or a layout. A size is a step on its scale, such as sm, md, and lg. A state is a condition the instance moves through at runtime, such as hover, loading, empty, or selected. Never combine two axes in one value: a "compact-error" state is a compact size plus an error state. An axis with one value uses the id `default`. Value names are sentence case and at most 24 characters; descriptions are one sentence of at most 120. List a variant or size that cannot appear in a state in `unsupported` with a reason.
- The compiler stamps `data-blueprint-variant`, `data-blueprint-size`, and `data-blueprint-state` on every reusable root, so its CSS selects on all three. Do not set them on the root element yourself.
- `slots` are the places a placement can fill: `{ "id", "name", "description", "accepts" }`, where `accepts` lists `text`, `graphic`, `brand-mark`, `primitive:<id>`, or `component:<id>`. Mark each in the source with `data-blueprint-slot="<id>"`, or use a bare `<slot>` for the `default` slot. Declare `"slots": []` when nothing can be customized. A placement that fills a slot with content it does not accept fails to compile.
- `uses` lists every primitive and component the source renders, once each, as `{ "kind", "id", "reason" }`. A component is built from at least one; a primitive may only use primitives. Token groups go in `tokenGroupIds`, never in `uses`.
- `platforms` lists where a reusable runs: one or more of `web` (a website or web app), `mobile` (a native phone app), and `desktop` (a native desktop app). A component's platforms must fit inside the platforms of everything it uses, so a component built from `nav-bar` is `mobile` only. Prefer shared primitives before platform-specific ones.
- `accessibility` says in at most 200 characters what role it has and how assistive technology announces it. Each note and hint is at most 200 characters. `accessibility`, `tokenRoles`, `notes`, `implementationHints`, `implementationTargets`, `styleRefs`, and `styleEvidence` are for agents and never appear on the canvas. The canvas page for every primitive and component shows only its header, platforms, built from, variants, sizes, states, and slots, so the person reviewing sees the same layout for each.
- Screens and tokens have fixed shapes too, and validation rejects any other field. A screen carries `id`, `name`, `description`, `framePresetId`, `page`, `styleRefs`, `styleEvidence`, `notes`, `prototypeOnly`, `implementationHints`, `implementationTargets`, `prototype`, and `sections`. Add `version` and `productionRelationship` only when they apply; a production relationship carries `kind`, `notes`, and the route fields its kind needs. A section carries `id`, `name`, `description`, `styleRefs`, `styleEvidence`, `uses`, `prototypeOnly`, `notes`, `implementationHints`, and `implementationTargets`, and each use is `{ "kind", "id", "reason" }` plus an optional `binding`. A token group carries `id`, `name`, `description`, `styleRefs`, `notes`, and `tokens`, and each token carries `id`, `name`, `type`, `value`, `description`, and `styleRef`. Write `[]` or `false` when a field has nothing to record.
- Screen, section, and token names are sentence case and at most 32 characters; page and token group names are at most 24. Screen and section descriptions are at most 200 characters, and page, token group, and token descriptions at most 120. Each note, hint, and reason is at most 200.
- Write the prose on every reusable, screen, and token in Simplified Technical English, because agents read it with no person to resolve what it means. This covers descriptions, use and unsupported reasons, slot and value descriptions, accessibility, notes, hints, production relationship notes, and component group, page, token group, and token descriptions. It does not cover the copy inside screens. Write sentences of at most 25 words with one idea each. Start each field with a capital letter and end it with a period. Do not use semicolons, phrasal verbs such as "spin up", marketing words such as "seamless", or a noun for an action, such as "perform an analysis". Keep "may" or "could" when the doubt is real. Validation rejects each of these with its fix. `validate` also returns `prose` advisories on passive voice, compound tenses, and two words for one action. Rewrite each one, unless the wording is deliberate, such as "selected" used as an adjective.
- Blueprint writes the description, accessibility, notes, and value and slot text of its own primitives, and every sidecar carries it unchanged. Validation rejects edits to it, and `migrate` restores it. Put app guidance for a primitive in `implementationHints`, and describe each value or slot you add.
- A sidecar that `init` makes with `"start": "inspo"` has no brand yet. It starts with `inspo.json` and an empty `inspo/` folder, and the brand comes from the inspo board. Use this order:
  1. When the person pastes an image link in chat, call the `inspo` tool with the `add` operation. Put the link in `url`. Put a kebab-case name in `id` that says what the image shows. Put the words of the person about the image in `note`, exactly as they wrote them.
  2. Set `aspects` to the parts of the image that the person points to. Set `stance` to `avoid` when the person shows the image as a look to avoid.
  3. Write in `reading` what you take from the image for its aspects.
  4. Propose one direction for each aspect with the `direction` operation. Pass `aspect`, `statement`, and the `entryIds` that it comes from.
  5. Show the directions to the person. Set `status` to `approved` only after the person approves the statement in chat.
  6. Write `brand.json` and the marks under `brand/` from the approved directions. Validation rejects `brand.json` until the person approves one direction.
- Git ignores the images in `inspo/`, and `inspo.json` keeps the link of each image. After a fresh clone, call `inspo` with the `sync` operation to download the images again. Use the approved directions and the notes of the person as the reference when you change tokens, primitives, components, or screens.
- `brand.json` is the brand guideline: name, tagline, personality, voice, marks, fonts, and usage rules. `fonts` lists each font family as `{ "family", "source", "assets" }`, with `source` `asset` or `system`. Each `font-family` token names a declared family or a generic family, and each `@font-face` loads a file from the `assets` of its family. `migrate` fills `fonts` from the font tokens and the `@font-face` rules. The starter ships a placeholder brand; replace it with the app's real brand before designing screens. Each mark is an SVG under `brand/` drawn with `currentColor`, plus `var(--brand-accent)` for a second color, so its variants can recolor it from color tokens. Outline wordmarks to paths instead of setting live text, and declare each mark's clear space and minimum size. Place the logo in screens and components with `<blueprint-use kind="brand-mark" ref="<mark-id>" variant="<variant-id>">` instead of pasting SVG markup, so every placement redraws when the brand changes. Size it with a class (it defaults to `1em` tall) and add `aria-hidden="true"` when nearby text already names the brand; otherwise it is labeled with the brand name. Brand marks are not declared in `uses`. Write interface copy in the brand voice and pick token values that express its personality.
- Build in layers: `brand.json` sets the direction, tokens encode it, primitives inherit the tokens, components compose primitives, and screens compose components and primitives. A screen should not need a look the lower layers cannot express. When it does, change the tokens or add a component instead of styling the screen one-off, so every screen stays inside the brand.
- Every screen belongs to a declared page and every component to a declared group. `screens.json` lists pages such as Web, Mobile, or Landing under `pages`, and each screen names one in `page`. Each page is its own canvas. List the screens of each page in the order that a person moves through them. The full-screen view uses this order for the Left and Right arrow keys. `components.json` lists `groups`, and each component names one in `group`. Reuse a page or group when the work fits it. To start a new one, declare it first with a kebab-case `id`, a sentence-case `name` of at most 24 characters, and a one-line `description` of at most 120. Validation rejects undeclared pages and groups.
- Run the `validate` tool in `baseline` mode after each batch of edits, and fix every error before you report the work. For implementation-bound work, also call it in `readiness` and `strict` modes. Readiness reports evidence and pending decisions, and does not replace strict validation. The `init`, `inspo`, `migrate`, `explore`, `promote`, and `restore` tools validate their own result in `baseline` mode. Do not call `validate` again on that result.
- Review with the `serve` MCP tool using `{ "project": "<this-folder>" }`. Before handing work back, clear the `findings` that `validate` returns; they are the design findings the canvas marks, each fixable in the file its `location` names. When you hand work back, add `"focus": "<kind>:<id>"` for the boundary you changed and share the returned URL so the person lands on it. When the person refers to "this", "that", or the selected element, call the `selection` tool to read what they selected in the canvas before editing. A selection made inside an exploration names its candidate; edit that candidate's returned files, and treat "this one" as the candidate to promote only when the person explicitly chooses it. Capture a declared condition with `capture` using a `screen:<id>` boundary plus its named `state`, `viewport`, and PNG `out` path. Capture a `component:<id>` or `primitive:<id>` the same way to check your own work; it crops to the boundary, takes a `variant` and `size`, and uses `viewport` only for its width.
- Screenshots, diffs, review manifests, and canvas inspection are evidence of what was reviewed, not editable source or dependency truth. Keep generated evidence under ignored `.blueprint-artifacts/` and do not commit it by default.
- Keep this folder single-project. Blueprint is a prototype and handoff surface, not a production service runtime, dashboard, registry, code generator, or cross-app project manager.
