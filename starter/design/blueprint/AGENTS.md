# Blueprint Agent Instructions

This folder is an app-owned Blueprint sidecar. Work sidecar-first and preserve the authority of each layer:

- Start with the Blueprint MCP `validate` tool using `{ "project": "<this-folder>" }`, then use `index` to discover stable boundary IDs. Use focused `query` calls and deep `extract` packets before reading the canvas DOM. Every validation error names the field and ends with `Fix:` and the exact change to make; apply it as written.
- When a tool reports that this folder is on an older schema, run the `migrate` tool, with `dryRun: true` first to see what it changes. It applies every mechanical change itself and returns the validation of the result; each remaining error is a decision for you, such as a component's platforms or a state's description. Fix them all before other work.
- Structured JSON owns stable IDs, declarations, named states, dependency relationships, production relationships, targets, review conditions, and saved exploration/history metadata. Keep `manifest.json`, `brand.json`, `tokens.json`, `primitives.json`, `components.json`, and `screens.json` internally consistent; keep each saved comparison in `explorations/<id>.json` and each prior canonical version in `history/<screen>-v<n>.json`.
- Every primitive, component, and screen declares governed HTML/CSS; there is no source-less format. Governed primitive HTML/CSS is the canonical reusable implementation. Primitive pages, components, and screens must instantiate that same source. Governed component HTML/CSS owns reusable assemblies. Screen HTML/CSS owns unique semantic hierarchy, responsive layout, media, effects, and art direction.
- Compose reusable boundaries with `<blueprint-use kind="primitive|component" ref="<stable-id>" variant="<variant>" size="<size>" state="<state>">`; an omitted attribute takes that axis's default. Declare every rendered reusable dependency in JSON; do not duplicate a recurring control in screen-local markup or add an app-specific Blueprint runtime branch. Blueprint replaces the authoring element with the referenced app root and annotates that root directly, so write layout selectors against semantic component/primitive roots rather than `<blueprint-use>`.
- Slot content belongs to the source that wrote it. A reusable placed inside another reusable's slot (a `text` label in a dialog, an `icon-tile` in a row's leading slot, a `status` in a table cell) is declared on the screen section or component whose HTML contains it, not on the container. Only declare it on the container when every instance of that container renders it; the container then keeps the credit. Slot elements match by balanced tags, so slot content may nest the same tag.
- Use token CSS custom properties for reusable colors, type, spacing, sizing, shape, shadow, and motion. Theme the app by changing the values of the existing roles in `tokens.json`; add a role only for a genuinely new meaning, never a parallel palette that restates existing roles. Record deliberate screen-local literals in `prototype.localValueExceptions` with the exact CSS property and literal value; strict validation rejects undeclared color literals and lengths that restate a same-role token. Instantiate control primitives with `<blueprint-use>` rather than hand-building native buttons, inputs, or selects; mark a deliberate native control with `data-blueprint-native="<reason>"`.
- Surfaces nest sequentially. Roots marked `data-blueprint-surface` (surface, card, grouped list, pressable row) take the next level of the `color.surface` to `color.surface-6` ladder after their nearest marked ancestor, so a card inside surface 3 renders at level 4. Mark app-added container primitives the same way instead of assigning them a fixed fill.
- Phone frames render the screen full-bleed at the preset size with the iOS status bar and home indicator drawn over it, as on device. Keep content clear of them with `var(--blueprint-safe-area-top)`, `-right`, `-bottom`, and `-left`, which every compiled screen receives from its frame preset; do not hard-code insets or draw status bars in screen source. Browser frames keep their toolbar outside the preset viewport.
- Keep fonts, images, and media inside `manifest.prototypeHost.assetRoots`, list screen assets in `prototype.assetRefs`, and keep sources self-contained. Do not add remote assets, undeclared filesystem refs, arbitrary JavaScript, or nondeterministic runtime state. Review links must remain safe local destinations and compile to inert metadata; forms must not declare actions or submitting controls in the static no-network slice.
- A new sidecar starts with exactly two empty base frames: `screen:home` on `phone` and `screen:web-home` on `desktop-web`, each backed by an empty screen source. Map real app tokens and recurring controls, then fill those sources before adding more routes or states. Do not invent product copy to fill an empty canvas.
- Keep frame naming structured: `productionRelationship.routePath` owns the route and `name` owns the short plain-language frame name. Blueprint derives the visible `Route · Frame name` label. If multiple screen records intentionally share both values, give every one a unique consecutive positive integer `version` starting at `1`; Blueprint then appends `· Vn`. Omit `version` for a single frame, and do not put routes, machine IDs, states, viewports, or version markers inside `name`.
- Use the MCP `explore` tool for two to five alternatives to one exact screen state and viewport. Edit only the returned candidate HTML/CSS sources, use exploration queries and `serve` with `explorationId` for review, and do not add candidates to `screens.json`. Leave unresolved explorations active or archive them; never delete their saved baseline or candidate sources. Call `promote` only after the person explicitly chooses a candidate and supply all current digests returned by inspection so stale work cannot overwrite a newer canonical screen silently. Use history queries plus `restore` when the person chooses a prior version; restoration must preserve the outgoing current screen as the next immutable history entry.
- `primitives.json` carries the closed Blueprint primitive set: the 33 building blocks every app shares, from button and input to table row. Keep exactly this set and never add or remove a primitive. Blueprint owns each primitive's id, name, group, platforms, defaults, and its floor of variants, sizes, states, and slots. Primitives take on this app's design through token values; restyle their sources and add variants, sizes, states, and slots above the floor as the app needs. An app-specific piece, such as a bento grid, a stat chip, or a rank emblem, is a component in `components.json` built from primitives. Validation rejects removed primitives and values below the floor, and strict validation rejects primitives outside the set.
- Primitives and components are reusables: presentational pieces that receive data and present it by the rules of the foundations, with no business logic. Both are written in one shape, and every field is required: `id`, `name`, `description`, `group`, `platforms`, `uses`, `variants`, `sizes`, `states`, `unsupported`, `slots`, `prototype` (`source`, `styles`, `localValueExceptions`), `tokenGroupIds`, `tokenRoles`, `accessibility`, `notes`, `implementationHints`, `implementationTargets`, `styleRefs`, `styleEvidence`, and `prototypeOnly`. Validation rejects any other field, so put nothing else on a reusable.
- Ids are kebab-case. Names are sentence case and at most 32 characters, such as "Empty state", not "Empty State"; descriptions say what it is and when to use it in at most 200 characters.
- `variants`, `sizes`, and `states` are each `{ "default": "<id>", "values": [{ "id", "name", "description" }] }` with at least one value. A variant is a design choice the placement keeps, such as primary or ghost, a tone, or a layout. A size is a step on its scale, such as sm, md, and lg. A state is a condition the instance moves through at runtime, such as hover, loading, empty, or selected. Never combine two axes in one value: a "compact-error" state is a compact size plus an error state. An axis with one value uses the id `default`. Value names are sentence case and at most 24 characters; descriptions are one sentence of at most 120. List a variant or size that cannot appear in a state in `unsupported` with a reason.
- The compiler stamps `data-blueprint-variant`, `data-blueprint-size`, and `data-blueprint-state` on every reusable root, so its CSS selects on all three. Do not set them on the root element yourself.
- `slots` are the places a placement can fill: `{ "id", "name", "description", "accepts" }`, where `accepts` lists `text`, `graphic`, `brand-mark`, `primitive:<id>`, or `component:<id>`. Mark each in the source with `data-blueprint-slot="<id>"`, or use a bare `<slot>` for the `default` slot. Declare `"slots": []` when nothing can be customized. A placement that fills a slot with content it does not accept fails to compile.
- `uses` lists every primitive and component the source renders, once each, as `{ "kind", "id", "reason" }`. A component is built from at least one; a primitive may only use primitives. Token groups go in `tokenGroupIds`, never in `uses`.
- `platforms` lists where a reusable runs: one or more of `web` (a website or web app), `mobile` (a native phone app), and `desktop` (a native desktop app). A component's platforms must fit inside the platforms of everything it uses, so a component built from `nav-bar` is `mobile` only. Prefer shared primitives before platform-specific ones.
- `accessibility` is one sentence of at most 200 characters on its role and how assistive technology announces it. `accessibility`, `tokenRoles`, `notes`, `implementationHints`, `implementationTargets`, `styleRefs`, and `styleEvidence` are for agents and never appear on the canvas. The canvas page for every primitive and component shows only its header, platforms, built from, variants, sizes, states, and slots, so the person reviewing sees the same layout for each.
- `brand.json` is the brand guideline: name, tagline, personality, voice, marks, and usage rules. The starter ships a placeholder brand; replace it with the app's real brand before designing screens. Each mark is an SVG under `brand/` drawn with `currentColor`, plus `var(--brand-accent)` for a second color, so its variants can recolor it from color tokens. Outline wordmarks to paths instead of setting live text, and declare each mark's clear space and minimum size. Place the logo in screens and components with `<blueprint-use kind="brand-mark" ref="<mark-id>" variant="<variant-id>">` instead of pasting SVG markup, so every placement redraws when the brand changes. Size it with a class (it defaults to `1em` tall) and add `aria-hidden="true"` when nearby text already names the brand; otherwise it is labeled with the brand name. Brand marks are not declared in `uses`. Write interface copy in the brand voice and pick token values that express its personality.
- Build in layers: `brand.json` sets the direction, tokens encode it, primitives inherit the tokens, components compose primitives, and screens compose components and primitives. A screen should not need a look the lower layers cannot express. When it does, change the tokens or add a component instead of styling the screen one-off, so every screen stays inside the brand.
- Every screen belongs to a declared page and every component to a declared group. `screens.json` lists pages such as Web, Mobile, or Landing under `pages`, and each screen names one in `page`; each page is its own canvas. `components.json` lists `groups`, and each component names one in `group`. Reuse a page or group when the work fits it. To start a new one, declare it first with a kebab-case `id`, a `name` of at most 24 characters, and a one-line `description` of at most 120. Validation rejects undeclared pages and groups.
- Run the `validate` tool in `baseline` mode after structural edits. For implementation-bound work, also call it in `readiness` and `strict` modes; readiness reports evidence and pending decisions, and does not replace strict validation.
- Review with the `serve` MCP tool using `{ "project": "<this-folder>" }`. Before handing work back, clear the `findings` that `validate` returns; they are the design findings the canvas marks, each fixable in the file its `location` names. When you hand work back, add `"focus": "<kind>:<id>"` for the boundary you changed and share the returned URL so the person lands on it. When the person refers to "this", "that", or the selected element, call the `selection` tool to read what they selected in the canvas before editing. A selection made inside an exploration names its candidate; edit that candidate's returned files, and treat "this one" as the candidate to promote only when the person explicitly chooses it. Capture a declared condition with `capture` using a `screen:<id>` boundary plus its named `state`, `viewport`, and PNG `out` path. Capture a `component:<id>` or `primitive:<id>` the same way to check your own work; it crops to the boundary, takes a `variant` and `size`, and uses `viewport` only for its width.
- Screenshots, diffs, review manifests, and canvas inspection are evidence of what was reviewed, not editable source or dependency truth. Keep generated evidence under ignored `.blueprint-artifacts/` and do not commit it by default.
- Keep this folder single-project. Blueprint is a prototype and handoff surface, not a production service runtime, dashboard, registry, code generator, or cross-app project manager.
